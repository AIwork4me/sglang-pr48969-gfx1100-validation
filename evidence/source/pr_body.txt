## Motivation

Since #42092, RDNA defaults to the Triton attention backend. Its grouped decode kernel (`_decode_grouped_att_m_fwd`) applies MI300-tuned launch hints on every HIP GPU: `waves_per_eu=1`, `matrix_instr_nonkdim=16`, `kpack=2`, with 4 warps (from #3255).

On RDNA3.5 (gfx1151, Strix Halo; wave32):
- `waves_per_eu=1` lets the compiler use 246 VGPRs per wave, so 5 waves fit per SIMD. Without it, 156 VGPRs and 9 waves.
- `matrix_instr_nonkdim` and `kpack` produce identical code on RDNA. ROCm/aiter#5917 drops `kpack` from its gfx1151/gfx1201 configs for the same reason, extending the gfx1100 cleanup in ROCm/aiter#5217.

GQA decode at batch is limited by how many KV loads are in flight, so with these hints the kernel reads the KV cache 1.4-2.7x slower once ~8+ requests are running. ROCm/aiter#2402 reaches the same conclusion for its unified attention on RDNA: `waves_per_eu` 8 on gfx1151, against 2 on CDNA.

## Modifications

On gfx115x, `_gfx115_grouped_num_warps` drops the hints and uses 2 warps. It keeps the existing config where dropping them wasn't measured to win:

| Case | Why the hints stay |
|---|---|
| MLA (`BLOCK_DPE > 0`) | compute-bound; dropping the hints is 0.80-0.97x |
| fp8 KV | dequant is emulated on RDNA3.5; mixed results, down to 0.85x |
| head_dim > 128 | neutral at head_dim 256: 0.98-1.02x at batch 4-64, ctx 4k/16k (no hints, 4 warps) |
| `batch * head_tiles < 8` | tiny grid (programs per KV split) at long context; e.g. 1 request on a 2-KV-head model at 32k is 0.69x |

Scope:
- Only gfx115x. It reuses the existing `is_gfx115_supported()`, as `unquant.py` does.
- Under CUDA graphs, `batch` is the captured (padded) batch size, so the choice is made per graph bucket. For example, a real batch of 3 on a 2-KV-head model replays the batch-4 graph and drops the hints.
- CDNA, other RDNA targets, CUDA, the MHA kernel (`_decode_att_m_fwd`) and the stage-2 reduce are unchanged.
- gfx1150 and gfx1152 are the same RDNA3.5 ISA family, so they're gated in, but only gfx1151 (40 CUs) was measured. They have fewer CUs, so the direction (more loads in flight on LPDDR) should hold, but the tiny-grid threshold of 8 is unvalidated there. Happy to narrow to gfx1151 if preferred.
- Other RDNA targets (gfx1100, gfx1201) likely benefit too. They're left out until measured; a follow-up can widen the gate with their numbers.

**Deterministic inference.** The gate depends on batch size. On this GQA path, verified bitwise on gfx1151 with Triton 3.6, a request's output doesn't change when the launch config switches; this is a measurement for this kernel and toolchain, not a general property (the MLA tuning in the same file notes `num_warps` can reorder accumulation).
- Checked directly: one request alone (hints kept) vs the same request inside batches of 2/3/4/8/16 (hints dropped, 2 or 4 warps).
- Per-request splits come from a fixed 256-token tile, as deterministic mode uses.
- Its output row is bitwise identical in all 60 combinations of shape (16/2 d128, 28/4 d128, 64/8 d64, 16/1 d128, and 16/4 d256 from an earlier revision that still changed head_dim 256), bf16/fp16, and context 100/4k/16k.
- A served check isn't possible on RDNA yet: `--enable-deterministic-inference` fails at startup there, because its batch-invariant matmul needs 99,328 B of LDS against 65,536 (#48968).

**Follow-up:** the stage-2 reduce (`_fwd_kernel_stage2`) hard-codes `waves_per_eu=4, mnk16, kpack=2` on all HIP too. It's a small kernel, so it's left for a separate change.

## Accuracy

- **Kernel outputs:** bitwise identical to main on 127/128 cases of a sweep through `decode_attention_fwd`. The sweep covers head_dim 64-576, GQA groups 1-128, page sizes 1/16/64, ragged lengths, logit cap, sinks, fp16, and 32k context.
- **The one exception:** an MLA ragged-batch case, where main itself returns NaN at random. This PR leaves the MLA path on identical code, and the case still flips between runs. It's a pre-existing bug: #48967.
- **GSM8K, full 1,319** (`sglang.test.few_shot_gsm8k`, 5-shot, parallel 64):

## Lean decode on gfx1151

On main, a default gfx1151 server fails during CUDA-graph capture: Lean decode needs 66,560 B of LDS against 65,536. #46912 fixes that. With both PRs, `lean_capture_policy` captures Lean for GQA decode at batch >= 16, so Lean, not the kernel changed here, would run at those batch sizes.

As shipped (BLOCK_N 64, 4 warps, CU-sized grid), Lean doesn't beat the grouped kernel with this PR on gfx1151 in any served configuration we measured. Each arm ran twice and the runs agree within ~2%. Served, this PR + #46912, Lean off vs on (main + #46912 measures the same as Lean on):

| Model | Load | Lean off vs on |
|---|---|---|
| Qwen3-0.6B, equal lengths (ms/step) | 1k in, c=16 / 32 / 64 | 1.43x / 1.58x / 1.08x |
| | 8k in, c=16 / 32 | 1.71x / 1.82x |
| Qwen3-0.6B, mixed lengths (tok/s) | 2k in, c=16 / 32 / 64 | 1.26x / 1.27x / 1.23x |
| | 16k in, c=16 / 32 | 1.29x / 1.32x |
| Llama-3.1-8B, mixed lengths (tok/s) | 2k in, c=16 / 32 / 64 | 1.07x / 1.10x / 1.10x |
| | 16k in, c=16 | 1.11x (median ITL 1.41x) |

Mixed lengths use `--random-range-ratio 0.25`. At 16k input, throughput includes a lot of prefill, which neither decode kernel runs, so median ITL is the closer measure of decode speed. At kernel level, the grouped kernel beats Lean in every mixed-length cell (batch 16-64, context 1k-16k), by 1.30-1.81x. With equal lengths, Lean wins only at batch 64: by ~5% at 1k/4k context and by 1.58x at 16k.

Lean hasn't been tuned for wave32 and may hit the same waves-in-flight limit this PR removes, so this is about its current config. A possible follow-up once both PRs land: skip Lean in `lean_capture_policy` on gfx115x. That only changes the CUDA-graph capture; the eager-path `lean_decode_seqlen_gate` (used outside CUDA graphs; 64K average tokens at batch 1, relaxing with batch) stays as is; that path wasn't measured here. #46912's crash fix is needed either way. Happy to coordinate with #46912.
